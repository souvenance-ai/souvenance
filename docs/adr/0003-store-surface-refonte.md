# The store surface of the refonte: hot curation over weight and read-signal

souvenance v0.2.0 rebuilds the store surface verb by verb instead of porting it 1:1 — the legacy `Store` is raw material, and every verb must earn its place against observed agent usage. Three verbs die (`update`, `delete`, the standalone `relations`) and the `tags` ledger leaves with the reads (no observed customer — tags as a _filter_ survive through `where`); `weight` and the `access_count` read-signal are dropped, and curation becomes a STATUS: `hot` joins the state machine as the curated sub-state of `active` (#38, revised 2026-10-25) — hot memories are what the checkin ritual serves a fresh session. Schema v6 drops the dead columns and migrates the legacy recover's basket (active directives, summaries, and open objectives) to `status = 'hot'`, so an existing individual checks in with the same memories it always did — now by explicit status instead of kind convention. `kind` is a required column with a free vocabulary — demanded at birth by `store`, a revision may reclassify it (supersede), a merge inherits it when the sources agree and demands a verdict when they disagree (#31, revised 2026-10-25). Search ranks by bm25 alone: search wants to search everywhere. Reads project the graph — `{out, in}` edges at depth 1, a `depth` option expanding out-edges (out expands, in informs). Unlink is a correction among the living: both endpoints must be living (`active` or `hot`), which makes the supersedes/merges bridges untouchable by construction. There is no delete: terminations are deprecate and supersede; persistent memory obliges. And every memory carries an authored `summary` — the condensation that lets checkin and search serve more memories per call; owed at write time when the content runs past the ceiling, and always itself beneath it.

## Considered options

- **Port 1:1, prune later** — keep every verb and column, mark the unused. Rejected: the surface ships as the product's contract; a catch-all invites agents into rituals nobody performs (observed: weight and the read signal untouched).
- **Keep `kind` a free metadata tag** — the refonte's original ruling (2026-10-24). Rejected on data (#31, 2026-10-25): the real v0.1 store carries `metadata.kind` on 219/219 rows with a coherent vocabulary, so "kinds unreliably tagged" is not reproducible from real usage; and `dream`/`vision` rule the enum out — hence a required column with a free vocabulary, backfilled `'unclassified'` where a row carries none, `$.kind` stripped from every row's metadata in the same migration (one source of truth, no divergence invariant, no doctor check). v6 was reshaped in place rather than bumped to v7: the version never shipped, and the cheap-now window closes at the merge to `main`.
- **Keep weight/access_count as ranking inputs** — simplify around them. Rejected: two hidden feedback mechanisms (the search read-signal bumped access_count behind the caller's back) for a ranking no agent tuned; hot is visible, explicit, and agent-controlled.
- **Hot as an addition to the kind blocks** — the legacy recover keeps directives/summaries/objectives and gains hot. Rejected for v0.2.0: four curation mechanisms where one explicit gesture suffices; the kind-block caps silently dropped what they did not serve.
- **Migrate the basket by weight (≥ 0.8 floor)** — the only mechanical signal the legacy carried. Rejected in favor of kind: the floor was a doctor recommendation, not an enforced convention; the kind basket reproduces exactly what the legacy recover served.
- **A `hot` table of ids instead of a state of its own** — membership as its own relation. Rejected twice: as a parallel table beside the status column it would need a second write or another trigger to keep the hot-only-while-active invariant (the column cools in the same UPDATE that changes the status); since #38 (2026-10-25) hot IS a state — the machine's own — and a side table would re-create exactly the divergence one column kills. A table earns its place only if hot entries carry their own data (multiple curated sets, priorities).
- **Rename `active` to `cold` for thermal symmetry (#38)** — the pair cold/hot reads cleanly. Rejected: hot is a SUB-STATE of active, not its sibling — renaming asserts a temperature partition the machine's semantics deny (the refusals operate on the living = active + hot, a vitality set, not a temperature one); the V2 column default `'active'` is baked into the frozen V1–V5 chain, so the rename forces either a table rebuild or a second spelling of the birth state (the exact divergence the kind column buried); and the checkout's `isolated_living` check reads the living set — a hot memory can be isolated, the widening is deliberate.
- **Rename `hot` to `curated`** — more precise, more formal in an API surface. Rejected: the ritual's vocabulary is thermal end to end (the hot block, heat/cool, setHot, no_hot), and a rename would churn every surface mid-port to buy formality alone. The name's job — marking what a fresh session reads first — is done.
- **`hot_since` (curation recency ordering)** — a single column with both membership and since. Rejected: any time-based serving order decays — long-standing directives would sink below freshly curated notes, or owe a constant re-curation to stay visible. The checkin has no cap: order never drops anything, it only guides attention.
- **Derive the summary mechanically or by LLM at write time** — the store stays a mechanical primitive (no LLM dependency, no cost, no non-determinism) and the agent — who knows the content — authors the condensation. Read-time truncation alone was rejected: no write-time enforcement, and the point of a long decision rarely sits in its first characters.

## Consequences

- Schema v6 gains the `hot` STATUS and `summary`, drops `weight`/`access_count` (and never adds a hot column — v6 was reshaped twice before shipping, #31 then #38: a v5 store has no hot column to drop, and the basket flips `status = 'hot'` directly). The migration is irreversible (the columns go) but preserves the legacy recover's basket via kind — old stores open and migrate. Migrated long rows keep `summary = null`: the condensation obligation starts with the refonte's writes.
- With hot a state, the old hot-only-while-active INVARIANT is unrepresentable — the contradiction it policed (hot on a terminal status) cannot be encoded in one column. The doctor's `hot_without_active` check retires (#38, `DOCTOR_CHECK_COUNT` 6 → 5). The discipline survives as shape: supersede transfers the status to the head, merge unions it, setHot is the machine's only reversible edge (`active` ↔ `hot`), and every termination cools for free — the status just moves.
- `summary` is authored at `store`/`supersede`/`merge` and never after: a revision of the condensation is a supersede. The successor always authors its OWN summary — the source's never carries over (a summary condenses one content; the revision's content is new). The ceiling (`MAX_SUMMARY_LENGTH`, 400 characters) is fixed by the store, not configurable; checkin serves summaries by default so a fresh session reads the whole hot set without flooding its context.
- `stats` loses `total_accesses` and the `active_memories` convenience (`memories_by_status` serves it), gains `memories_by_kind` — the latter reads the required `kind` column with 100% coverage (kind-less memories no longer exist; `unclassified` appears like any other kind). The hot count follows the same precedent: it reads through `memories_by_status['hot']` (#38) — no second spelling of a count the status ledger already carries.
- `update`, `delete`, and the `relations` verb register in the backlog with reactivation criteria, as does the `tags` ledger removed at the reads port ([Backlog: store surface — future tracks](https://github.com/souvenance-ai/souvenance/issues/28)).
- The server and MCP surfaces adjust accordingly: no PATCH/DELETE memory endpoint, no relations endpoint; a curation transition appears (setHot: `active` ↔ `hot`); checkin serves the hot block as summaries; search ranks by bm25; the CLI exposes `--content`/`--summary` as a display projection.
- `Store.open` requires an explicit `dbPath` — the path is policy (config, manager), never a silent default the library guesses.
