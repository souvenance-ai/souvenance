# The store surface of the refonte: hot curation over weight and read-signal

souvenance v0.2.0 rebuilds the store surface verb by verb instead of porting it 1:1 — the legacy `Store` is raw material, and every verb must earn its place against observed agent usage. Three verbs die (`update`, `delete`, the standalone `relations`) and the `tags` ledger leaves with the reads (no observed customer — tags as a _filter_ survive through `where`); `weight` and the `access_count` read-signal are dropped, and a single `hot` flag takes over curation: hot memories are what the recover ritual serves a fresh session. Schema v6 drops the dead columns and migrates the legacy recover's basket (active directives, summaries, and open objectives) to hot, so an existing individual recovers with the same memories it always did — now by explicit flag instead of kind convention. `kind` returns to being a free metadata tag. Search ranks by bm25 alone: search wants to search everywhere. Reads project the graph — `{out, in}` edges at depth 1, a `depth` option expanding out-edges (out expands, in informs). Unlink is a correction among the living: both endpoints must be active, which makes the supersedes/merges bridges untouchable by construction. There is no delete: terminations are deprecate and supersede; persistent memory obliges. And every memory carries an authored `summary` — the condensation that lets recover and search serve more memories per call; owed at write time when the content runs past the ceiling, and always itself beneath it.

## Considered options

- **Port 1:1, prune later** — keep every verb and column, mark the unused. Rejected: the surface ships as the product's contract; a catch-all invites agents into rituals nobody performs (observed: kinds unreliably tagged, weight and the read signal untouched).
- **Keep weight/access_count as ranking inputs** — simplify around them. Rejected: two hidden feedback mechanisms (the search read-signal bumped access_count behind the caller's back) for a ranking no agent tuned; hot is visible, explicit, and agent-controlled.
- **Hot as an addition to the kind blocks** — recover keeps directives/summaries/objectives and gains hot. Rejected for v0.2.0: four curation mechanisms where one explicit gesture suffices; the kind-block caps silently dropped what they did not serve.
- **Migrate the basket by weight (≥ 0.8 floor)** — the only mechanical signal the legacy carried. Rejected in favor of kind: the floor was a doctor recommendation, not an enforced convention; the kind basket reproduces exactly what recover served.
- **A `hot` table of ids instead of the column** — membership as its own relation. Rejected: the hot-only-while-active invariant must hold at every status transition; the column cools in the same UPDATE that changes the status, a table would need a second write or another trigger. A table earns its place only if hot entries carry their own data (multiple curated sets, priorities).
- **`hot_since` (curation recency ordering)** — a single column with both membership and since. Rejected: any time-based serving order decays — long-standing directives would sink below freshly curated notes, or owe a constant re-curation to stay visible. The recover has no cap: order never drops anything, it only guides attention.
- **Derive the summary mechanically or by LLM at write time** — the store stays a mechanical primitive (no LLM dependency, no cost, no non-determinism) and the agent — who knows the content — authors the condensation. Read-time truncation alone was rejected: no write-time enforcement, and the point of a long decision rarely sits in its first characters.

## Consequences

- Schema v6 adds `hot` and `summary`, drops `weight`/`access_count`; the migration is irreversible (the columns go) but preserves the recover basket via kind — old stores open and migrate. Migrated long rows keep `summary = null`: the condensation obligation starts with the refonte's writes.
- The hot invariant (hot only while active) is enforced at every status transition — supersede transfers, merge unions, every termination cools; a doctor check will verify it mechanically (#13).
- `summary` is authored at `store`/`supersede`/`merge` and never after: a revision of the condensation is a supersede. The successor always authors its OWN summary — the source's never carries over (a summary condenses one content; the revision's content is new). The ceiling (`MAX_SUMMARY_LENGTH`, 400 characters) is fixed by the store, not configurable; recover serves summaries by default so a fresh session reads the whole hot set without flooding its context.
- `stats` loses `total_accesses` and the `active_memories` convenience (`memories_by_status` serves it), gains `hot_memories` and `memories_by_kind` (a `json_extract` ledger — kind stays a free metadata tag, no column; a kind-as-constraint revision is charted, #31).
- `update`, `delete`, and the `relations` verb register in the backlog with reactivation criteria, as does the `tags` ledger removed at the reads port ([Backlog: store surface — future tracks](https://github.com/souvenance-ai/souvenance/issues/28)).
- The server and MCP surfaces adjust accordingly: no PATCH/DELETE memory endpoint, no relations endpoint; a hot toggle appears; recover serves the hot block as summaries; search ranks by bm25; the CLI exposes `--content`/`--summary` as a display projection.
- `Store.open` requires an explicit `dbPath` — the path is policy (config, manager), never a silent default the library guesses.
